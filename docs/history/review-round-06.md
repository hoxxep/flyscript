v1.0 is coherent, but it isn't world-class yet: it's a well-informed synthesis with too many separate mechanisms. Count them: owned values, `mut`/`readonly` borrows, `from`, regions, pools, `Arc`, five marker traits, record rows, effect rows, three handler-arm kinds, three closure kinds, `try`/`Result`/`Fail`, `comptime`, refinements plus a solver, `@layout(soa)`, `par for`. That's more concepts than Rust in places. Great languages have a small core from which almost everything falls out. This round is about finding Flyscript's beautiful simplification.

**Step 1: argue against v1.0 first.** Before changing anything, give your five strongest objections to v1.0 as it stands, each with a concrete program that is unsound, unergonomic or impossible to write. You've agreed with every change so far; I want your independent judgment. Push back on anything below you think is wrong, with a reason.

**Step 2: rebuild v1.0 around a three-mechanism thesis: affine ownership, one row system, handlers for everything, plus `comptime` as the metalanguage.** Concretely:

1. **One row system for records, variants and effects.** Add **structural sum types** (TypeScript-style unions of tags, like OCaml polymorphic variants or Roc tag unions): `Fail<"Malformed" | "TooLarge" | ...R>`, or tags with payloads. Error types then compose automatically by row union, which should delete most of `From`, `mapErr` and `try ... else`. Nominal `enum` stays for abstraction. Records, variants and effect rows must share one row kind and one unifier.
2. **One error mechanism.** `Fail` is the effect. `Result` is just `Fail` reified as data (`Result.capture`), and `try` survives only at boundaries (FFI, or explicit reflection back from `Result`). Std I/O should use `uses Fail<IoError-tags>` directly.
3. **Allocation is an effect again; regions are handlers.** `Alloc` is an effect; the global allocator is its root handler; `region (r) { ... }` is a rank-2 scoped handler of `Alloc`. This removes the separate `Region<R>` API and the Pod-only restriction: `Vec`, `String` and `Box` just work inside a region. **The hard part you must solve explicitly:** if the allocator is an effect, a type like `Vec<T>` no longer records which region its memory lives in, so what stops a region-allocated `Vec` escaping the region? Options include an allocator/region index on owning types defaulting to the global heap (`Vec<T, R = Heap>`), inferring it the way effect rows are inferred, or something better. Choose the design that keeps signatures free of region noise in the common case.
4. **Iteration is a `Yield<T>` effect** (as in Koka), so `for (const x of xs)` handles `Yield` and generators and effectful iterators fall out for free (this also settles the "iterators with effects" question).
5. **Parallelism is a library.** `par(items, (p) => ...)`, whose closure is required by its type to have an empty effect row and a disjoint `mut` element, replaces the `par for` keyword. Say what the type system must provide for that to be expressible as a library signature.
6. **Layout is `comptime`.** `Soa(Particle)` is a `comptime` function returning the struct-of-arrays type (Zig's `MultiArrayList`). Delete `@layout(soa)` as a special case; keep `@layout(c)`/`packed` only if they can't also be `comptime`.
7. **Cut refinement types and the integer solver from v1.** Ranges and iterators eliminate bounds checks in the common case (as in Rust). Move refinements to future work.
8. **Expression-oriented core.** `if`, `match` and blocks are expressions yielding their last value; `return` stays allowed for TS familiarity. State the statement/expression rule precisely, including how it interacts with semicolons.
9. **Region-pointer sharing.** v1.0 makes `In<R, T>` `Sync` "when `R` is frozen read-only", so a trait depends on program position. Move that into the `Async.scope`/`par` typing rule (the region is passed down as read-only capability) so traits stay purely type-directed. Re-check the whole marker-trait set: can `Pod`, `Send`, `Sync`, `val` and `Drop` be reduced?

**Step 3: positioning and targets.**
- Add **WebAssembly** as a first-class target alongside native. TS developers live in the browser and at the edge. Say how `Io` maps onto a WASI/JS host handler.
- Add a short **"Why Flyscript"** section comparing honestly with Rust, Roc, Koka, Hylo, Mojo, Zig and TypeScript: what Flyscript can do that each can't, and what it gives up.

**Output:** v1.1 as one complete, self-contained document (every v1.0 section that survives, rewritten to the new core; don't drop anything without listing it under "Removed in v1.1"). Open with the objections from Step 1 and how v1.1 answers each, then a **concept-count table: v1.0 vs v1.1**, showing what was deleted, what merged into rows, handlers or `comptime`, and what remains primitive. Rewrite the full HTTP example and the deterministic-simulation example in v1.1. The best result is a spec that is noticeably *shorter* in its core than v1.0 while expressing more.
