1. **Second-classness should propagate through *every* type, nominal ones included.** Program 2 uses `counts.getMut(word)` returning `Option<mut u64>`, but v1.4 requires nominal type parameters to be first-class, so `Option<mut T>`, `Result<readonly T, E>` and a `struct` view with a `mut` field are all illegal. Replace the special rule with one uniform rule: **class(τ) = max over all components and type arguments**, for records, tuples, variants, nominal `struct`/`enum` and containers alike. `Option<mut u64>` is simply a second-class `Option`, and `struct Cursor { buf: readonly u8[]; pos: usize }` is simply a second-class struct (Program 1's `Scanner` already relies on this!). The only constraint left is the one that matters: second-class values can't escape (fields of first-class values, escaping closures, untied returns, `Send` across fibers). Update §6, the core calculus `class` function and the grammar comment on `FieldType`.

2. **Borrows are transparent: no deref operator.** Program 2 writes `*slot += 1`, but `*` is never specified and isn't TypeScript. Make borrow bindings behave like the value they borrow (as in Hylo `inout`/C++ references): reading `slot` reads the referent; assigning `slot += 1` writes through a `mut` borrow; borrow bindings can't be re-pointed. `T*` raw pointers keep explicit `unsafe` dereference (`ptr.read()`/`ptr.write(v)`).

3. **Fiber vs generator drop semantics collide.** Since a `Fiber<T>` is a continuation, and dropping a continuation unwinds it, Program 7's `const _ = s.spawn(...)` *cancels every connection immediately*. Define the ownership split: **a spawned fiber is owned by its `Scope`**; `spawn` returns a `Fiber<T>` join handle whose drop merely detaches it (the scope still joins it at exit, and failure still cancels siblings). A `Gen<T>` owns its continuation, so dropping it unwinds. State both, and the shared runtime primitive underneath.

4. **Effect forwarding for stored continuations.** When `ga.next()` resumes a continuation captured inside `generate`, which handler receives effects the generator performs other than `Yield` (e.g. `Io` or `Fail`)? Specify deep-handler semantics: operations not handled by the captured handler are forwarded to the dynamic context of whoever *resumes* the continuation, which is why `Gen<T, E>.next()` has type `Option<T> uses ...E`. Show how `Fail` raised inside a generator propagates out of `next()`.

5. **Grammar and examples must agree.**
