This is a strong direction. Two decisions, then the problems I want fixed in the next version.

**Decisions**
1. The language is called **Flyscript** (file extension `.fly`).
2. It uses **TypeScript-style syntax**: TS's surface, not its semantics. Keep: `function`, arrow lambdas `(x) => x + 1`, `const`/`let`, `name: Type` annotations, `<T>` generics, `interface`, `type` aliases, `import`/`export` ES modules, object-literal-style struct construction, `for (const x of xs)`, template strings. Drop: structural typing (types are nominal), `any`, `null`/`undefined` (use `Option<T>`), class inheritance, `number` (use `i32`, `u8`, `f64`, `usize`...), exceptions as untyped `throw`. Add what TS lacks: `match` as an expression, sum types with payloads, effect rows, capabilities, regions, `comptime`. Every extension must read like idiomatic TypeScript to a TS developer: no `/ [Effects]` sigils, no Rust `::` paths, no `fn`.

**Problems with v0.1 that v0.2 must resolve with a decision each (pick one; don't give me options):**
1. **Ownership vs Perceus.** Perceus is reference counting with reuse; with truly affine `own`, reuse is static and needs no count. v0.1 uses both without saying which. Decide the default ownership model for heap values (affine-with-moves like Rust/Hylo, or RC with reuse like Koka/Swift), and where the other one appears, if at all.
2. **Type inference.** Hindley-Milner can't survive `comptime` types-as-values, rank-2 regions, refinements and traits together (Zig has no inference for this reason). Specify bidirectional local inference: what must be annotated (signatures? effects?) and what is inferred.
3. **Effects × affinity.** A handler that resumes a continuation twice duplicates affine values and live borrows. State the rule (I expect: continuations are one-shot, as in OCaml 5) and how tail-resumptive vs suspending handlers are compiled.
4. **Regions × destructors.** "Freed in one instruction" holds only if nothing in the region has a destructor or owns an outside resource. Specify what types may be allocated in a region, whether region values may point out to owned/RC/`iso` values, and what happens to them on region exit.
5. **Reclaiming `val`.** Deeply frozen data shared across actors must be reclaimed somehow: atomic RC, ORCA-style protocol, or immortal/epoch-based. Choose and justify.
6. **Naming clashes and loose claims.** `ref T` (capability) clashes with `Ref<r, T>` (region pointer): rename one. `step_physics` is declared pure but writes through `&mut`: define the purity rule for mutable parameters precisely. Move "pure functions compile straight to GPU kernels" to a non-goals/future section. Fix the claim that dependent type checking is undecidable (checking is decidable; the cost is writing proofs).
7. **Capabilities.** Reduce the five capabilities (`own`, `mut`, `ref`, `iso`, `val`) to the minimal orthogonal set and give their subtyping/conversion lattice (e.g. how `iso` becomes `val` by freezing, how borrowing works) in TS-flavored modifiers (like `readonly`).

**Format for v0.2.** Write it as a real specification, not a pitch: drop marketing numbers ("15 ns", "80% of data", "0 nanoseconds"). Sections: goals and non-goals; lexical syntax and grammar sketch (EBNF for declarations, types, effect rows, match); types (primitives, structs, enums, generics, traits/interfaces, refinements); ownership, capabilities and regions with the typing rules stated informally but precisely; effects and handlers; concurrency and parallelism; `comptime`; modules; the compiler pipeline; and an "open questions" list containing only things that genuinely can't be decided yet. Re-do every code example in Flyscript syntax, and include one complete ~40-line example program (e.g. a tiny HTTP handler that parses a request in a region, uses `Fail` and `AsyncIO`, and spawns two concurrent fetches in a structured scope).
