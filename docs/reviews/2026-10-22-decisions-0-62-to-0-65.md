## Question

# Review request: decisions made since your review of phases 3–5

You reviewed the LLVM back end, the M:N scheduler, direct handlers, sockets and the web framework (your review is attached as context). Acting on it and on the author's own list of weak areas, these decisions were made. I want your strongest objections — unsoundness, semantics that will hurt users, things that will not scale — ranked by severity. Cite the decision by number.

1. **Panics stop their task without cleanup** (spec §5.7). Native code could not unwind a panicking task (that needs a check after nearly every call, or zero-cost unwinding tables), while the reference evaluator and the JavaScript back end ran `defer`s on a panic. Rather than build unwinding, all three now agree: a panic ends its task where it is — no `defer`s, no drops — except that a `Mutex` its body held is given back; the scope's other tasks are cancelled and unwind normally, running their cleanup; the panic continues outward and always ends the program (panics cannot be caught).
2. **Tasks unpinned by a `const` context accessor** (§8.3, §11). The state compiled code reads of the running task (failure being raised, unwinding, stopping, handler stack) moved from thread-locals into a per-task `fly_ctx`. Code reaches it through `fly_ctx* fly_cx(void) __attribute__((const))`, defined out of line and `noinline`, reading the thread's current-context pointer that the scheduler sets whenever it switches a task in. The argument: within one activation of a function the running task never changes, wherever it migrates, so caching or recomputing the result anywhere in the activation gives the same pointer; hence `const` is sound even though the definition reads a thread-local. All runtime thread-locals are reached through `noinline` accessors with an empty `asm volatile` barrier on the returned address. The scheduler code that switches tasks uses a non-const accessor. A task waiting on a queue holds that queue's spin lock across its switch-out; its worker releases the lock after the switch completes, so no other worker can resume a half-switched task.
3. **Operations without arms pass on** (§5.2). A `handle` may give some of its effect's operations no arm; such an operation goes to the handlers around the `handle`, as if its arm were `op(x) resumes k => k(Eff.op(x))`. The checker makes such a `handle` itself perform the effect (and errors if the surrounding code does not allow it). Compiled code synthesizes the forwarding arms. A program's own handler of `Io` is honored by every back end; to keep this free for programs that never handle `Io`, the lowering checks whole-program whether any `handle` handles `Io`, and only then makes each `Io` operation test at run time whether a user handler of `Io` is on the handler stack.
4. **The `Page` effect** (web/). `run` handles `effect Page<Model> { show(m: readonly Model): void; }` around each `update`, so an update about to wait for the server can say `m.adding = true; Page.show(m);` and the page renders the in-progress state. This needed a checker fix: an operation's argument for a `readonly` parameter is now lent to the arm, as a call's is.
5. **§9 restated.** Terms, judgments with a loan set, the rules, five guarantees (type safety, memory safety, effect safety, data-race freedom, deterministic destruction) for programs without `unsafe`, and how each is established without a mechanized proof: three implementations that must agree under sanitizers, a generator of well-typed programs (520 seeds so far, all agreeing in four implementations under ASan/UBSan/leak checking), and mutants breaking one ownership rule each, which the checker must reject.
6. **Holding by use** (§4.1). One rule replaces three: code that takes hold of a place without saying how (a match arm, a closure capture, a `const` from a borrow) takes the weakest hold its uses need — copy, `readonly`, `mut`, or move.

Also tell me which of your earlier findings you still think are open, given: lexical scoping of direct-handler arms was already correct (arms run with the handler stack set to the handle's outer); sockets have separate read and write waiters and are affine, so closing one while another task waits on it cannot happen; a `Mutex` body cannot perform `Io`, and `join` jobs are pure, so a body's `join` never runs code that takes a lock.

## Answer

### Verdicts

- **(1) Panics stop their task without cleanup (`§5.7`):** **Agree with changes.** Stopping the panicking task without running its `defer`s/drops is sound *only* because panics cannot be caught and always terminate the program, **except** there is a severe deadlock/UB hazard when a panic occurs inside a nested fiber (`handle` body or `Gen.next()`) or while a sibling task holds a stack-borrowed buffer or waits on a channel/reply owned by the panicking task (`§6.1`, `§6.2`, `§6.3`).
- **(2) Tasks unpinned by a `const` context accessor (`§8.3`, `§11.2`):** **Disagree with `__attribute__((const))` on `fly_cx(void)` when `handle` fibers or `Gen` share a task (`§5.2`, `§5.5`); Agree with the post-switch spinlock release.** Within a single *task*, switching into a child fiber (`handle` or `Gen.next()`) either shares the same `fly_ctx` (in which case a nested fiber overwrites `err`/`unwinding` of its parent fiber!) or changes the active fiber context on the same thread (in which case `__attribute__((const))` or cross-function CSE during LTO caches the wrong context!).
- **(3) Operations without arms pass on (`§5.2`):** **Agree with changes.** Synthesizing `op(x) resumes k => k(Eff.op(x))` is clean and ergonomic, **except** when an omitted operation has a **borrowed parameter (`readonly T` or `mut T`)** (`§5.1`: `Io.read(fd: Fd, buf: mut u8[])`, `Io.write(fd: Fd, buf: readonly u8[])`) and the handler has another arm whose continuation `k` escapes or is non-direct (`§5.3`).
- **(4) The `Page` effect and lending operation arguments to the arm (`§5.3`, `web/`):** **Agree with changes.** Lending `readonly` / `mut` operation arguments to the arm fixes `Page.show(m)`, **except** `§5.3`'s rule (*"a parameter whose type can hold a borrow is usable in a resumptive arm only until the arm calls `k`, and never past the arm"*) has a soundness hole when the arm **mutates through a `mut` operation parameter** or passes a borrowed operation argument into a closure/container captured by outer state before calling `k`, or when `k` is never called (`§5.3`).
- **(5) `§9` restated (Core calculus & guarantees):** **Agree with changes.** The restatement is much sharper, but two formal rules in `§9.3` contradict the rest of the spec or omit a required premise (`Region` escape via `Cell.set` / `RegionList.push`, and `Handle` loan tracking when an arm does not resume `k`).
- **(6) Holding by use (`§4.1`):** **Agree with changes.** Unifying match arms, closures, and borrow bindings under "weakest hold its uses need" is a great simplification, **except** for two ambiguous/unsound edge cases: (a) an arm that moves one field of a struct/tuple and *mutates* or *borrows* another field before the arm ends, and (b) a closure whose body only *reads* a non-`Copy` binding `x` when the closure itself is later forced to **escape** (`§4.3`).
- **(Earlier findings status):** Direct-handler lexical scoping is **partially open** (for `Fail` tunnelling through inner `try`/`catch`, see Problem 3 below); Socket waiter safety is **still open** on cancellation (`§6.3`, see Problem 4 below); `Mutex` + `join` deadlock is **still open** if `join` steals *tasks* or if all workers spin on `Mutex` while a lock holder is in `join` (see Problem 5 below).

### Problems (Ranked by Severity)

#### 1. [Decision 1] Panicking without drops in a child task deadlocks the parent `Io.scope` (so the panic never terminates the program!) and violates `§6.3` in-flight I/O buffer safety (`§5.7`, `§6.1`, `§6.2`, `§6.3`)

Look at Decision 1 (`§5.7`):
> *It stops the current task where it is: a bug leaves no state worth cleaning up from, so the task's `defer`s do not run and what it owns is not dropped — except that a `Mutex` its body held is given back. It then fails the task's scope (§6.1), whose other tasks are cancelled and unwind, running their cleanup as cancelled tasks do; once they have, the panic continues in the task that opened the scope, and so on outward, until it ends the program.*

Now trace what happens in two completely ordinary concurrent programs when a task panics and **does not drop what it owns**:

**Program 1A (Scope deadlock on panic via un-dropped `Sender` / `Reply` / child `Gen`):**
```ts
import { channel } from "std/sync";

export function main(): void uses Io {
  const [tx, rx] = channel<i32>();

  Io.scope((s) => {
    // Task 1: owns `tx`, panics before closing/dropping `tx`!
    s.spawn(() => {
      const tx2 = tx.clone();
      const x = 1 / 0; // PANIC! `tx2` is NOT dropped!
      tx2.send(x);
    });
    tx.close();

    // Task 2: has a `defer` that drains `rx` (or sends a final message and waits for `Reply`).
    // Under §5.6 / Decision 6b ("Cleanup runs to its end"), cancellation is MASKED during `defer`!
    s.spawn(() => {
      defer {
        for (const msg of rx) { /* drain remaining items */ }
      };
      Io.sleep(Duration.secs(10));
    });
  });
}
```
Trace what happens when Task 1 panics on `1 / 0`:
1. Task 1 stops where it is. Because Task 1's locals are **not dropped**, `tx2` is never dropped! The channel's sender count remains `1`.
2. The scope cancels Task 2. Task 2 wakes from `Io.sleep` and enters its `defer` block.
3. Because Decision 6b (`§5.6`) masks cancellation while a `defer` runs, Task 2's `for (const msg of rx)` waits in `rx.recv()` for the last `Sender` (`tx2`) to close.
4. Because Task 1 skipped dropping `tx2`, `rx.recv()` waits **forever**, the `Io.scope` never finishes waiting for Task 2, and the panic **never exits the program**!
- Even simpler: what if the scope body itself (the parent fiber of `Io.scope`!) is parked in `rx.recv()` (`const bad = Io.scope((s) => { const reader = s.fork(...); for (const hit of rx) { ... } })` — **literally the example in `§6.2`!**) when `reader` panics before `tx.close()`?!
  Wait: in `§6.2`'s example:
  - The scope body is blocked in `for (const hit of rx)` (`rx.recv()`).
  - `reader` (which owns `tx`) panics on an integer overflow in `parseLine(line)`.
  - If `reader` stops without dropping `tx`, `tx` is never closed! Unless `rx.recv()` in the scope body is immediately interrupted by the child's panic, the scope body hangs in `rx.recv()` forever!

**Program 1B (Use-after-free of stack buffer when a task panics inside a nested `Io.scope` or `handle` fiber while in-flight kernel I/O holds a stack buffer, `§6.3`):**
```ts
export function serve(conn: mut Socket): void uses Io {
  let buf: u8[512] = repeat(0); // Lives on Task A's stack!
  Io.scope((s) => {
    s.spawn(() => {
      // Borrows `buf`... wait: `buf` is readonly if shared, so `conn.write(buf)`:
      try { conn.write(buf); } catch (_) {} // In-flight kernel write reading `buf` on Task A's stack!
    });
    // Scope body panics!
    const _ = 1 / 0;
  });
}
```
If the scope body panics, it must wait for the spawned task's in-flight `conn.write(buf)` to be cancelled and drained (`§6.3`) *before* Task A's stack is freed or exited.

**Fix:**
If a panic must always end the program (`§5.7`: *"until it ends the program. Panics are for bugs"*), why does a panic on a worker thread try to cooperatively unwind outer scopes all the way back to `main` in native code at all, **or** if you want the simulator (`SimIo`) to catch/report panics cleanly while native code aborts:
- In native multi-threaded mode, a panic prints the panic message and calls `_Exit(1)` / `abort()` immediately (no outer task can catch a panic anyway!).
- In `SimIo` (single-threaded test runner, where `Io` is virtual and you may test panic diagnostics), aborting the whole simulated world immediately on panic (rather than waiting for sibling tasks' `defer`s to drain channels whose `Sender`s were leaked by the panicking task!) avoids hanging the test runner when a producer task panics while a consumer's `defer` is reading from a channel or `Pending.wait()`.

#### 2. [Decision 2] Marking `fly_cx()` as `__attribute__((const))` is unsound under LTO when a task runs a fiber-backed `handle` or `Gen.next()` (`§5.2`, `§5.5`, `§11.2`)

In Decision 2, you write:
> *Code reaches it through `fly_ctx* fly_cx(void) __attribute__((const))`, defined out of line and `noinline`, reading the thread's current-context pointer that the scheduler sets whenever it switches a task in. The argument: within one activation of a function the running task never changes, wherever it migrates, so caching or recomputing the result anywhere in the activation gives the same pointer; hence `const` is sound even though the definition reads a thread-local... The two are `llvm-link`ed and optimized once.*

Stop and trace what happens when **two functions are inlined into one activation by LLVM after `llvm-link`**, or when a function calls **`Gen.next()` / a fiber-backed `handle`**!

First, ask: **Does a fiber-backed `handle` (`§5.2`) or a `Gen` (`§5.5`) have its own `fly_ctx` (or its own `err` / `unwinding` / `handler_top`), or does it share the parent task's `fly_ctx`?**
Let's check both possibilities — **both break!**

**Case A: Suppose a fiber-backed `handle` / `Gen` has its own `fly_ctx` (so switching into the `handle` fiber or `Gen.next()` changes the thread's current `fly_ctx*` pointer).**
Because `llvm-link` links all user functions and `runtime.c` into **one LLVM module** and runs LLVM's optimizer (`opt -O2`), look at what happens when `fly_cx()` is declared `__attribute__((const))` (`readnone` in LLVM IR):
1. Even if `fly_cx()` is `noinline`, LLVM's `EarlyCSE` / `GVN` pass knows that a `readnone` (`__attribute__((const))`) function with `void` arguments **always returns the exact same pointer throughout the entire program**!
2. If Caller calls `fly_cx()` (getting `%cx`), then calls a helper `step(mut gen)` which is **inlined** into Caller, and inside `step` (or inside a callback on the other side of a fiber switch that gets inlined) `fly_cx()` is called again: LLVM's `GVN` replaces every call to `fly_cx()` with the first `%cx`!
3. Even worse: if `fly_cx()` is defined in `runtime.c` **and `runtime.c` is `llvm-link`ed into the same module**, then inside `runtime.c` itself (e.g. scheduler or fiber-switch helpers), if any function calls `fly_cx()`, LLVM sees two calls to a `readnone` function across `fly_fiber_switch()` and folds the post-switch `fly_cx()` to the pre-switch `fly_cx()`!

**Case B: Suppose a fiber-backed `handle` / `Gen` shares the parent task's `fly_ctx` (so `fly_cx()` is per-task, not per-fiber).**
Now look at what happens when a generator or resumptive `handle` unwinds when dropped while an outer `try` or `handle` is active (`§5.3`, `§5.5`):
```ts
function nums(): void uses Yield<i32> {
  defer {
    // Runs when `g` is dropped!
    // Inside this `defer`, we use `try ... catch`!
    try { throw #Ignore; } catch (_) {}
  };
  yield 1;
  yield 2;
}

export function main(): void uses Io {
  try {
    let g = generate(() => nums());
    const _ = g.next(); // Pauses `nums()` after `yield 1`
    throw #OuterErr;    // Sets `cx->err = #OuterErr` and starts unwinding `main`!
                        // Unwinding `main` drops `g`!
                        // Dropping `g` switches into `nums()`'s fiber (`cx->unwinding = 1`)
                        // to unwind `nums()` and run its `defer`!
  } catch (e) {
    // What are `cx->err` and `cx->unwinding` when `g`'s drop returns to `main`?!
    match (e) { #OuterErr => println("caught outer") }
  }
}
```
Trace what happens if `g`'s fiber and `main`'s fiber share a single per-task `fly_ctx`:
1. `main` throws `#OuterErr`: `cx->err = #OuterErr`.
2. While `main` unwinds toward `catch (e)`, `main` drops local `let g`.
3. `Gen.drop` sets `cx->unwinding = 1` and switches into `nums()`'s suspended fiber to unwind it.
4. `nums()`'s `defer` runs `try { throw #Ignore; } catch (_) {}`, which **overwrites `cx->err = #Ignore`** (and clears it when caught), and when `nums()` finishes unwinding its fiber, `Gen.drop` clears `cx->unwinding = 0`!
5. Control returns to `main`'s `catch (e)` — **and `cx->err` has been clobbered by `#Ignore` (or NULL)!**

**Fix (solves both Case A and Case B cleanly):**
1. **Per-fiber vs per-task state:** `err`, `unwinding`, and `handler_top` are **per-fiber** (or saved/restored in a stack Variable when `Gen.drop` / `Cont.drop` switches fibers during unwind!).
2. **Never use `__attribute__((const))` (`readnone`) on a function whose value changes across fiber switches in an LTO-linked module.**
   You wrote in `§11.2`: *"which a function computes once a call"*.
   You don't need `__attribute__((const))` to compute `cx` once per function call!
   In `ir.fly` / `llvm.fly` / `c.fly`, simply emit **one explicit call** `fly_ctx *cx = fly_get_cx();` at the **entry of each generated Flyscript function** that needs `cx` (or pass `fly_ctx *cx` as the first hidden parameter in your private LLVM ABI!).
   - Wait: look at passing `fly_ctx *cx` as parameter 0 of your private LLVM ABI (`selfhost/llvm.fly` *already* uses a private ABI for all Flyscript functions!):
     - Cost of `fly_cx()` call on every function entry: **0 instructions** (it's already in argument register `x0` / `rdi`, which is callee-saved or passed down!).
     - Needs `__attribute__((const))` hack? **No!**
     - Works across task migration to another OS worker thread? **Yes!** Because `cx` points to the task/fiber struct on the heap, which moves with the task across OS threads!

#### 3. [Decision 3 & Earlier Finding 2] Direct Handlers + Forwarded Operations: Two Soundness Bugs (`§5.2`, `§5.3`)

**Bug 3A: Synthesizing `op(x) resumes k => k(Eff.op(x))` for omitted operations is unsound when `x` is a borrow (`mut u8[]` or `readonly u8[]`) and another arm of the `handle` is non-direct (`§5.1`, `§5.2`, `§5.3`).**
Look at `§5.1`, `§5.2`, and `§6.4`:
```ts
// §6.4: Handling only `sleep` of `Io`, letting `read` and `write` pass on!
let buf: u8[64] = repeat(0);
const r = handle {
  const n = Io.read(fd, mut buf); // `read` is NOT listed in `with Io` -> forwarded!
  Io.sleep(Duration.ms(10));
  n
} with Io {
  // Suppose this arm is non-direct (e.g. stores `k`, or can fail, or has code after `k()`):
  sleep(d) resumes k => {
    const res = k();
    slept += d.toMs();
    res

```
Now look at the synthesized forwarding arm for `Io.read(fd: Fd, buf: mut u8[])` under Decision 3 (`§5.2`):
> *as if its arm were `op(x) resumes k => k(Eff.op(x))`*

Look at what that synthesized arm does:

And now read `§5.3` ("Arguments are lent to the arm"):
> *So a parameter whose type can hold a borrow is usable in a resumptive arm only until the arm calls `k`, and never past the arm...*
Wait: in `k(Io.read(fd, mut buf))`, `Io.read(fd, mut buf)` runs *before* `k(...)` is called, so while `Io.read` is running in the outer `Io` handler, `k` (the suspended inner fiber) is still paused at `Io.read`, holding its stack frame alive — **that part is fine!**
**HOWEVER**, what if the inner body passed a borrow of a **local inside the `handle` block** to an omitted operation `Eff.borrowOp(s: str): str from s` that **returns a borrow tied to `s`**?!
```ts

// Synthesized arm for `intern`:
// intern(s) resumes k => k(Store.intern(s))
```
In `intern(s) resumes k => k(Store.intern(s))`:
- `s` is a borrowed parameter of the arm (`str`, class 2).
- `Store.intern(s)` returns a `str` **borrowed from `s`**.
- And then the arm passes that `str` **into `k(...)`**!
- Does your ownership checker (`§5.3`: *"a parameter whose type can hold a borrow is usable in a resumptive arm only until the arm calls `k`"* — i.e., its loans cannot be live at or across `k(...)`!) allow passing a borrow derived from `s` *as the argument to `k(...)`*, or does `own.fly` reject the synthesized arm `k(Eff.op(x))` whenever `Eff.op` returns a borrow tied to `x`?!
Check this! If `own.fly` checks synthesized arms (or if someone writes `op(x) resumes k => k(Eff.op(x))` by hand for an op returning `readonly T from x`), forbidding `x`'s loans from reaching `k(...)`'s argument rejects valid forwarding! Conversely, allowing `x`'s loans into `k(...)` is ONLY sound for the resumption argument of `k` itself (because `x` came from the caller of `op(x)` inside `k`, where `x`'s owner lives!).

**Bug 3B (Earlier Finding 2 still open for `Fail`!): A direct handler whose arm calls `Eff.op()` (or a forwarded op!) where the *outer* handler for `Eff` is abortive or throws `Fail`, while the *inner* `handle` body has a `try ... catch`!**
In your question, you noted:
> *given: lexical scoping of direct-handler arms was already correct (arms run with the handler stack set to the handle's outer)*

Popping the direct handler stack when entering an arm fixes `Eff2` lookup, **yes** — **but what about `try ... catch` (`Fail`) when a direct arm calls an effect operation whose outer handler throws `Fail` (or aborts)?!**
Look at this program:
```ts
effect Ask { ask(): i32; }
effect Outer { get(): i32; }

function body(): i32 uses Ask {
  try {
    const x = Ask.ask();
    if (x == 0) { throw #BodyErr; }
    x
  } catch (e) {
    // Closed union: `e` can ONLY be `#BodyErr`!
    match (e) {
      #BodyErr => 10,
    }
  }
}

export function main(): void uses Io {
  try {
    const v = handle {
      handle {
        body()
      } with Ask {
        // Notice: `ask` arm has NO `Fail` in its own body!
        // It only performs `Outer.get()` and tail-resumes `k(...)`!
        // So Decision 3 classifies `with Ask` as a DIRECT handler!
        ask() resumes k => k(Outer.get())
      }
    } with Outer {
      // The outer handler for `Outer` throws `#OuterBoom`!
      get() resumes k => {
        if (true) { throw #OuterBoom; }
        k(42)
      }
    };
    println(`${v}`);
  } catch (e) {
    match (e) {
      #OuterBoom => println("caught OuterBoom in main"),
    }
  }
}
```
Trace what happens in your compiler on this program right now:
1. Look at `with Ask`: its arm `ask() resumes k => k(Outer.get())` resumes `k` once as its last act, and its arm has effect `Outer` — **not `Fail`**!
2. So `with Ask` is compiled as a **direct handler**: `body()` runs directly on the stack, and inside `body()`'s `try { const x = Ask.ask(); ... } catch (e)`, `Ask.ask()` is a direct function call to `ask_arm()`.
3. `ask_arm()` calls `Outer.get()`.
4. `with Outer`'s arm runs and executes **`throw #OuterBoom`**, which sets `cx->err = #OuterBoom` and returns!
5. Now `ask_arm()` sees `cx->err != NULL` and returns early to its caller — **which is inside `body()`'s `try { ... } catch (e)` block!**
6. `body()`'s `try ... catch (e)` sees `cx->err != NULL`, catches `#OuterBoom` as `e`, and enters `match (e) { #BodyErr => 10 }`, where `e` is `#OuterBoom` — **an impossible tag in `body()`'s closed `catch` union, crashing with an inexhaustive match panic or reading garbage payload!**

Run this program! Why did it happen? Because even though `ask`'s arm did not mention `Fail` directly, it performed `Outer.get()`, and the handler for `Outer` outside `with Ask` threw `Fail<#OuterBoom>` across the direct handler's stack frames!
**Fix:**
Either:
- A direct handler's arm must be **pure (`uses []`) or only perform effects whose handlers are also non-failing**, **OR** (much better and works for all arms!):
- Each `try` block has a lexical `try_depth` (or handler stack watermark): when `throw` sets `cx->err`, it records the active `handler_top` / `try_depth` of the current context; when `ask_arm` runs with `handler_top` popped to `with Ask`'s outer context, any `throw` inside `ask_arm` targets the `try` block outside `with Ask`, so `body()`'s inner `try ... catch` sees `cx->err_target_depth < body_try_depth` and **unwinds (`defer`/drops) without catching it**, letting `main`'s `catch` catch `#OuterBoom`!

#### 4. [Decision 4 & `§5.3`] Soundness Hole in Lending Operation Arguments to Resumptive Arms (`§5.3`)

In Decision 4 and `§5.3`, you changed operation parameters from move to lend:
> *An operation's argument for a `readonly` or `mut` parameter is lent to the arm, as a call's is (§5.3).*
> *So a parameter whose type can hold a borrow is usable in a resumptive arm only until the arm calls `k`, and never past the arm: it cannot be the arm's value, nor stored where the arm's end would leave it dangling. An abortive arm runs after the body has unwound, so it cannot use such a parameter at all.*

Look at what happens when an operation has a **class-2 view or borrow parameter** (or `mut` parameter) and a **resumptive** arm (`op(x) resumes k => ...`) **does NOT call `k` on some path** (or drops `k` *before* using `x`!):

```ts
effect Inspect {
  peek(s: str): void;
}

export function main(): void uses Io {
  handle {
    const localStr = "hello world".toString();
    Inspect.peek(localStr); // Lends `localStr` (which lives on the `handle` body's fiber stack)
  } with Inspect {
    // Resumptive arm (`resumes k`), so the checker allows using `s: str`!
    peek(s) resumes k => {
      drop(k);        // Unwinds the suspended body! `localStr` is DROPPED and freed here!
      println(s);     // USE-AFTER-FREE! `s` points into `localStr`'s freed heap buffer!
    }
  };
}

function drop<A, B, row E>(k: Cont<A, B, E>): void {}
```
Look at what happened:
1. The arm is a **resumptive arm** (`peek(s) resumes k => ...`).
2. `§5.3` says: *"So a parameter whose type can hold a borrow is usable in a resumptive arm only until the arm calls `k`, and never past the arm"*.
3. In the program above, the arm **never calls `k()`** — instead, it **moves/drops `k`** (`drop(k)`), which immediately unwinds the body fiber and frees `localStr`, and then the arm reads `s` (`println(s)`) **after `k` was dropped!**
4. What if the arm doesn't even call `drop(k)`, but has a local with a `Drop` destructor declared *before* `k` is implicitly dropped at the end of the arm, or what if `s` is used after `k` is moved into a helper function `consumeCont(k)`?

**Fix (`§5.3` & `own.fly`):**
In a resumptive arm `op(x) resumes k => armBody`, the borrowed operation parameters `x` do not borrow from the arm's frame — **they borrow from `k`!**
Formally, in `§9.2` / `own.fly`:
- Every parameter `x` of a resumptive arm whose type can hold a borrow carries a **loan of `k` (`{ k : ro }`)**!
- Because `k` is an affine value (`Cont`) that is **moved** whether it is called (`k(a)`), passed to a function (`drop(k)`), or stored (`#Item { item, rest: k }`), giving `x` a loan of `k` means the existing borrow checker (`§4.1`) **automatically forbids moving, calling, or dropping `k` while `x` (or any borrow derived from `x`) is still live**!
- That single rule ("an arm's borrowed parameters hold a `readonly` loan of `k`") replaces the ad-hoc prose in `§5.3` and makes `drop(k); println(s);` a standard move-while-borrowed error!

#### 5. [Decision 6] Two Edge Cases in "Holding by use" (`§4.1`, `§4.3`)

In Decision 6 (`§4.1`), you unified match arms, closure captures, and borrow bindings into one rule:
> *Code that takes hold of a place without saying how — a `match` arm binding its parts, a closure capturing a binding (§4.3), a name bound by `const` from a borrow — takes the weakest hold its uses need: a copy of a `Copy` value it only reads, a `readonly` borrow of anything else it only reads, a `mut` borrow of what it changes in place or lets go where it could be changed, and the value itself only if it moves it — an arm that moves a part takes the whole place, owning all it binds and dropping what it does not move on when it ends.*

Here are two programs where this single rule breaks or is ambiguous:

**Program 5A: A `match` arm that moves one binding `a` and borrows another binding `b` into a value returned from the `match`!**
```ts
type Pair = #Pair(String, String);

function takeFirstAndBorrowSecond(p: Pair): str {
  // Arm moves `a` (via `consume(a)`) and only reads `b` (via `b.asStr()`):
  match (p) {
    #Pair(a, b) => {
      consume(a);
      b.asStr() // Wait: `a` was moved, so the arm "takes the whole place, owning all it binds
                // and dropping what it does not move on when it ends"!
                // That means `b` is OWNED by the arm and DROPPED when the arm ends!
                // If `b` was held as a `readonly` borrow of `p` before upgrading to move,
                // does `b.asStr()` get rejected because `b` is dropped at the end of the arm?!
    }
  }
}
function consume(s: String): void {}
```
Look carefully at what `§4.1` says:
> *an arm that moves a part takes the whole place, owning all it binds and dropping what it does not move on when it ends.*

Suppose `p` is a local `let p = #Pair("hi".toString(), "there".toString());` and after the `match`, the function doesn't return `b.asStr()`, it stores `const slice = match (p) { #Pair(a, b) => { consume(a); b.asStr() } }; println(slice);`!
- If the arm hadn't moved `a`, `b` would be a `readonly` borrow of `p.1`, so `b.asStr()` would borrow `p`, which lives until the end of the function.
- Because the arm moved `a`, the arm **took the whole place `p` and drops `b` when the arm ends**!
- Make sure `own.fly` treats `b` in an arm that moves `a` as an **owned local of the arm** (dropped at the end of the arm, so no borrow of `b` can escape the arm!), **OR** allows partial moves out of structural sum/product patterns without dropping the unmoved parts at the end of the arm!

**Program 5B: A `match` arm on a value whose type implements `Drop` (`§4.1`, `§5.6`).**
```ts
struct Packet { header: String; body: String; }
impl Drop for Packet {
  function drop(self: mut Self): void {}
}

function takeHeader(pkt: Packet): String {
  match (pkt) {
    Packet { header, body } => header // Moves `header` out of `Packet`!
  }
}
```
In `§4.1` paragraph 1:
> *Moving a field out of a value moves only that field, unless the value's type implements `Drop`, from which no field may be moved.*
And in `§4.1` paragraph 5 ("Holding by use"):
> *an arm that moves a part takes the whole place, owning all it binds and dropping what it does not move on when it ends.*
Does `match (pkt) { Packet { header, body } => header }` allow moving `header` out of `Packet` (violating `§4.1` paragraph 1 and `§5.6` by skipping `Packet.drop` and only dropping `body`!), or does the checker forbid moving a pattern-bound part of a `struct` or `enum` that implements `Drop`?!
**Fix:** Explicitly state in `§4.1` ("Holding by use") that an arm may not move a part out of a type that implements `Drop` (just as field projection `x.f` may not).

#### 6. [Decision 5 & Earlier Findings] Two Gaps in `§9.3` and Two Earlier Findings Still Open (`§6.3`, `§6.5`, `§9.3`)

**1. `§9.3` (Region rule): Missing the "No owned resources" / outer-region-only premise.**
Look at `§9.3`'s Region rule:
> $\Delta, \rho \mid \Theta \mid \Gamma \vdash e : \tau / \text{Region}\langle\rho\rangle, \varepsilon \vdash \Theta' \quad \rho \notin \text{ftv}(\tau, \Theta', \varepsilon) \quad \text{no closure escaping } e \text{ captures data of } \rho$
>
> $\overline{\Delta \mid \Theta \mid \Gamma \vdash \text{region}(\rho)\ \{ e \} : \tau / \varepsilon \vdash \Theta'}$

Consider this program with nested regions `R1` (outer) and `R2` (inner):
```ts
region (R1) {
  const outerCell: Cell<R1, Option<Ref<R1, i32>>> = Cell.new(#None);
  // What stops an inner region `R2` from storing a `Ref<R2, i32>` into `outerCell` or `RegionList<R1, ...>`
  // if the type is erased or hidden in a closure or if `alloc` / `Cell.set` doesn't check outlives?!
}
```
In `outerCell`, the type is `Ref<R1, i32>`, so `R2` would have to unify with `R1` (prevented by $\rho_2 \notin \text{ftv}(\Delta)$). **Wait:** in `§9.3`'s Region rule, you checked $\rho \notin \text{ftv}(\tau, \Theta', \varepsilon)$, **but you forgot $\rho \notin \text{ftv}(\Delta, \Gamma)$!**
If $\rho$ were allowed to unify with an existing unification variable in $\Delta$ or a borrow in $\Gamma$ (e.g., assigning a `Ref<R2, i32>` through a `mut Option<Ref<R_var, i32>>` parameter or local in $\Gamma$ whose type is in the outer environment $\Delta$, not in $\Theta'$!), a `Ref<R2, T>` would escape `region (R2)` into the outer variable!
**Fix in `§9.3`:** Change $\rho \notin \text{ftv}(\tau, \Theta', \varepsilon)$ to $\rho \notin \text{ftv}(\Delta, \Gamma, \tau, \varepsilon)$.

**2. Earlier Finding 4B (Still Open!): Socket `close(fd)` during scope cancellation while an `Io.read`/`Io.write` on that `fd` was in flight (`§6.3`).**
In your question, you wrote:
> *sockets have separate read and write waiters and are affine, so closing one while another task waits on it cannot happen*

Agreed that two tasks cannot wait on the same `Socket` because `Socket` is affine!
**However**, look at **one task** waiting on a `Socket` when its `Io.scope` is cancelled (`§6.3`):
1. Task 1 on Worker 0 calls `conn.read(mut buf)`. `conn.read` registers Task 1 in `waiters[fd].read_waiter`, adds `fd` to `epoll`/`kqueue`, and parks Task 1.
2. While Task 1 is parked on `fd`, sibling Task 2 fails, cancelling the scope!
3. The scheduler wakes Task 1 for cancellation (`cx->stopping = 1`).
4. Meanwhile, on the Poller thread, the OS kernel just delivered an `EPOLLIN` / `EVFILT_READ` event for `fd`!
5. Task 1 unwinds its stack and runs `Socket.drop(conn)`, which calls `close(fd)`.
6. Check what happens in `runtime.c` when Task 1 wakes from `Io.read` due to cancellation (`cx->stopping = 1`):
   - Does `Io.read` clear `waiters[fd].read_waiter` under `waiters[fd].lock` **before** returning on the cancellation path?
   - If `Io.read`'s cancellation path returns early *without* clearing `waiters[fd].read_waiter`, then `waiters[fd].read_waiter` still holds a dangling pointer to Task 1's fiber (which is about to finish and be freed/pooled!), and when the Poller thread sees `EPOLLIN` on `fd` (or a reused `fd`), the Poller thread wakes the freed/reused fiber pointer!
   - Double-check that the cancellation exit path in `Io.read` / `Io.write` acquires `waiters[fd].lock` and nulls out `read_waiter` / `write_waiter` before unwinding.

**3. Earlier Finding 1 (`Mutex` + `join` helping):**
In your question, you wrote:
> *a `Mutex` body cannot perform `Io`, and `join` jobs are pure, so a body's `join` never runs code that takes a lock.*

That is true **provided** `join`'s work-helping loop **only steals from the `join` deque (pure closures) and NEVER steals from the task deque (`Io` tasks)**!
Verify in `runtime.c`: when a worker inside `join(a, b)` waits for `b` to finish and "helps with other work", it must **only** steal `join` jobs, never `Io` tasks (because an `Io` task stolen and run on that worker could call `m.lock()` on the very `Mutex` that the caller of `join` is currently holding on the same stack!).
