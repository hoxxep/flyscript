## Question

# Step 16's last items: derived functions over long chains in bounded stack

Context. Derived `Eq`, `Ord`, `Hash` (prelude, `comptime` reflection over `Type.info(T)`) take a value's last part last, as the function's result: `return self.[last].eq(other.[last])`, so comparing `struct Node { v: i64; next: Option<Box<Node>> }` along a list is a chain of calls in tail position through `Node.eq → Option<Box<Node>>.eq → Box<Node>.eq → Node.eq`. An optimized native build turns them into jumps (sibling-call optimization); a sanitized build (ASan/TSan, which disable it) and WebAssembly (no tail calls unless `-mtail-call`) recurse once per link and overflow on a list a million long. Drop glue is already bounded (spec 0.129: a nested drop is deferred to a worklist once the stack has less than a megabyte left). The derived `Clone` builds its value after cloning its parts, `{ v: self.v.clone(), next: self.next.clone() }`, and `Box.clone` is `Box.new(self.get().clone())`, so it recurses along a chain in every build. Spec §5.7: a stack that runs out is a panic of its task. Native code has no stack switching any more (tasks are state machines); every function in a cycle of calls checks its stack.

Backends: C (clang or gcc; cleanups are `__attribute__((cleanup))` frame records under -fexceptions, catch points are setjmp records), LLVM IR (landing pads), WebAssembly through LLVM (wasm EH), JavaScript, and a reference evaluator.

## Proposal 1: guaranteed tail calls where the signature matches

The compiler marks a call as `musttail` (LLVM) / `__attribute__((musttail)) return` (clang C; gcc 15 has it too) / `return_call` (wasm, `-mtail-call`, on by default in V8 ≥ 11.2) when: (a) the call's result is the function's result with nothing after it — no drop, no `defer`, no cleanup record, no catch point, not a state machine's step; (b) no argument points into the caller's frame (an argument is a scalar, a borrow param, or a place reached through a deref of a pointer the caller was given; not the address of a local); (c) the lowered prototypes match (in C, through a cast of the callee to the caller's function type, which for pointer parameters is ABI-identical). The spec then says: a call in tail position, which nothing is left to do after, to a function whose parameters and result are passed as the caller's are, is a jump, on every native and WebAssembly build (not JavaScript, which has no tail calls in V8). In practice: derived `Eq`/`Ord`/`Hash` compare and hash chains in constant stack everywhere but JavaScript.

## Proposal 2: derived `Clone` along the last part

Options I see:

- **(a) Destination-passing + tail calls.** `cloneInto(self, out: *T)` writes all but the last part, then tail-calls the last part's `cloneInto(&out->last)`; `Box.cloneInto` allocates and tail-calls into the payload; enums write the tag then tail-call into the payload. Needs uninitialized destinations (unsafe, in the prelude). Panic safety: a user `Clone` that panics midway leaves a half-built chain: either leaked (violates "every box dropped exactly once", which `--leaks` tests and §9.5 claims for the core) or the compiler must track which parts are initialized (drop flags for a value under construction).
- **(b) Two passes with an explicit stack.** For a struct/enum whose last part reaches the same type through `Option<Box<Self>>`/`Box<Self>`: walk the chain cloning each node's other parts into a `Vec` of nodes with the link `#None`, then link them from the end. O(n) extra memory, safe Flyscript, panic-safe (the `Vec` owns everything), but only for recognized link shapes.
- **(c) Grow the stack** (Rust's `stacker`/rustc `ensure_sufficient_stack`) at the existing stack checks of functions in cycles: run the call on a new heap segment. General (Show, user recursion), but brings back stack switching, unwinding across segments, sanitizer fiber annotations — what phase B removed.
- **(d) Accept** that `Clone` of a long chain panics with stack overflow, and document it (Rust's derived Clone and Drop overflow too; ours drops in bounded stack already).

I lean to Proposal 1 as stated, and for Clone to (a) with compiler-tracked initialization — or (b) if (a)'s panic safety costs too much complexity.

## Answer

### Verdicts

- **Proposal 1 (Guaranteed `musttail` where signatures match):** **Disagree as a general compiler/spec rule; Agree with changes only as a targeted lowering or with strict stack-free argument constraints.** In Flyscript, `match` on an `Option<Box<Node>>` or `enum` binds payload borrows as *stack locals* unless lowered to direct field-offset pointers; worse, casting function pointer types in C to force `__attribute__((musttail))` is undefined behavior in Clang/GCC (`-Wincompatible-function-pointer-types-strict` / CFI), and LLVM's `musttail` verifier rejects calls whenever local `alloca`s exist andASan is enabled unless those `alloca`s are `lifetime.end`'d and not referenced.
- **Proposal 2 (Derived `Clone` on deep chains):** **Disagree with (a), (b), and (c); Agree with (d) — or, if bounded-stack `Clone` is required, use iterative pointer-reversal / in-place hole-plugging on `Box` without compiler-tracked partial initialization.** Both (a) and (b) fail on the first non-last recursive child anyway (e.g., `#Add(Box<Expr>, Box<Expr>)` in `§3.3`), and (a) violates `§9.4` (leaks or drops uninitialized memory on panic) unless the compiler adds heap-chain partial-drop unwinding that doesn't exist anywhere else in the language.

### Problems

#### 1. [Proposal 1] `match` in Derived `Eq`/`Ord`/`Hash` Creates Frame-Local Borrows That Fail `musttail` (or Cause UB Under ASan) (`§3.5`, `§4.1`)

Look at the chain you described:
> `Node.eq → Option<Box<Node>>.eq → Box<Node>.eq → Node.eq`

Write out how derived `Eq` for `Option<T>` (`#Some(T) | #None`) is written in `comptime` Flyscript (`§3.5`, `§7.2`):
```ts
impl<comptime T: Type> Eq for T {
  function eq(self: readonly Self, other: readonly Self): bool {
    comptime match (Type.info(T)) {
      #Union(tags) => match ([self, other]) { // or nested match (self) { #Some(a) => match (other) { #Some(b) => a.eq(b) } }
        ...
      }
    }
  }
}
```
Trace what happens in the C and LLVM backends when `Option<Box<Node>>.eq` matches `self` and `other`:
1. If it writes `match ([self, other])`, the tuple `[self, other]` is a **local temporary on the stack** of `Option<Box<Node>>.eq`.
2. Even if it writes nested `match (self) { #Some(a) => match (other) { #Some(b) => a.eq(b) } }`, how does your lowering bind `a: readonly Box<Node>` and `b: readonly Box<Node>`?
   - If the pattern matcher copies the tag payload or stores the borrow pointer in a local `alloca` and passes `&local` (or if `a` is a local holding `&self->payload` and `Box.eq` takes `readonly Box<Node>`, i.e., `const Box_Node*`), check whether `a` is already a pointer (`&self->u.Some`) or a local!
   - Even when `a` is `&self->u.Some`, what about a `struct Wrapper { inner: i64 }` or a tag with a tuple payload `#Pair(i64, Box<Node>)`? In `#A(x)` (`§3.2`: *"Whatever its shape, `#A(x)` builds or binds a payload whole: `#Add(pair)` where `pair: [Expr, Expr]`"*), reflection in `Eq` uses `#[t.name](a)` to bind the payload whole (`§3.2`, `§7.2`)!
   - When a tag has multiple arguments `#Cons(i64, Box<List>)`, `Type.info(T)` says (`§7.2`):
     > `type TagInfo = { name: str; payload: Option<Type> }; // the one type of #A(T), or the tuple or record`
     If `#Cons(i64, Box<List>)` has payload `[i64, Box<List>]` and `#[t.name](a)` constructs/binds a tuple `[i64, Box<List>]` by copying the two fields into a local tuple `a` on the caller's stack frame, then `a.eq(b)` passes **the address of local `a` and `b` on the caller's stack** into `Tuple.eq(&a, &b)`!
   - Passing `&a` into a `musttail` call is **immediate use-after-free of the caller's stack frame** (and under ASan, `musttail` either fails to compile or triggers `stack-use-after-return`)!

And check your condition (c) for C:
> *(c) the lowered prototypes match (in C, through a cast of the callee to the caller's function type, which for pointer parameters is ABI-identical).*

In C, calling a function `bool Box_Node_eq(const Box_Node*, const Box_Node*)` through a cast `(bool (*)(const Option_Box_Node*, const Option_Box_Node*))Box_Node_eq`:
1. **Is strict Undefined Behavior in C11 (6.3.2.3p8)** — `const Box_Node*` and `const Option_Box_Node*` are pointers to incompatible struct types.
2. **Traps at runtime under Clang `-fsanitize=cfi` / `-fsanitize=function` (part of UBSan!)** and WebAssembly indirect-call type checks if ever indirect, and Clang's `__attribute__((musttail))` checker inspects the callee expression and warns/errors on mismatched pointee types or struct returns.
3. Why cast function pointers at all when, at the C / LLVM IR level, **all `readonly T` and `mut T` parameters in your ABI can simply be `const void*` / `void*` (or opaque `ptr` in LLVM IR)**?
   - In LLVM IR, since LLVM 15+, **all pointers are untyped `ptr`**! So `(ptr, ptr) -> i1` is **already** the exact same LLVM signature for `Node.eq`, `Option<Box<Node>>.eq`, and `Box<Node>.eq` without any cast!
   - In C, if `musttail` is used, only functions whose C parameter types are identical (or `const void*` in runtime helpers) are legal without UB.

#### 2. [Proposal 1] Do Not Put "Parameters Passed as the Caller's Are" in the Language Spec (`§11.3`)

Look at your proposed spec wording:
> *"The spec then says: a call in tail position, which nothing is left to do after, to a function whose parameters and result are passed as the caller's are, is a jump, on every native and WebAssembly build (not JavaScript, which has no tail calls in V8)."*

A Flyscript programmer cannot see "how parameters and result are passed" in the lowered ABI:
```ts
function f(x: i64): i64 { g(x, 0) } // 1 param vs 2 params: not musttail!
function a(x: readonly Node): bool { b(x, x) } // 1 param vs 2 params: not musttail!
function p(x: i32): i32 { q(x as i64) as i32 } // not musttail!
```
In LLVM, `musttail` requires **identical ABI parameter lists** (same number of arguments, same register/stack classes, same return type). In C with Clang `__attribute__((musttail))`, a 1-arg function cannot `musttail` a 2-arg function!
And in Flyscript, a tiny change by a user (adding a parameter with a default, or borrowing a local, or returning a value from a block that drops a local `String`) silently breaks the `musttail` requirement unless there is an explicit keyword or unless the promise in `§11.3` is scoped to what you actually guarantee:
- Look at `§4.4`:
  > *"What a box, a `Vec` or an `Arc` holds of a type that may hold itself, where such drops nest deeply, is dropped after the rest of the value holding it, so dropping a list a million long takes the stack a few nodes do"*
- Notice how `§4.4` states the guarantee **for the operation (`Drop`)**, not as a half-baked general TCO law that fails on JavaScript, fails in the reference evaluator, and fails whenever arity differs!
- If your goal is that derived `Eq`, `Ord`, and `Hash` do not overflow the stack on deep recursive types in native/Wasm builds, state **that** in `§3.5` / `§11.3` (or keep it an implementation improvement), rather than promising general tail-call elimination that breaks on arity mismatch.

#### 3. [Proposal 2] Why Option (a) ("Destination-Passing `cloneInto` + `musttail`") Is Broken on Panics and Trees (`§3.5`, `§5.7`, `§9.4`)

Trace what happens with Proposal 2(a) on this 20-line program:

```ts
struct Bomb { id: i64; }
impl Clone for Bomb {
  function clone(self: readonly Self): Bomb {
    if (self.id == 500_000) { panic("boom"); }
    Bomb { id: self.id }
  }
}
impl Drop for Bomb {
  function drop(self: mut Self): void {
    // must run for nodes 0..499_999, and MUST NOT run for uninitialized node 500_000!
  }
}

struct Node { b: Bomb; next: Option<Box<Node>>; }
impl Clone for Node;
```
Now run `Io.scope((s) => { s.spawn(() => { const c = head.clone(); }); })` where `head` has 1,000,000 nodes and node `500,000` panics inside `Bomb.clone`:
1. Under Proposal 1 + 2(a), `Node.cloneInto` has made **500,000 `musttail` jumps**!
   **There are NO stack frames on the call stack for nodes `0 .. 499,999`!** Their stack frames were overwritten by `musttail`!
2. Where is the pointer to the root `Box<Node>` (node `0`) that was allocated 500,000 `musttail` steps ago?!
   - Node `0`'s `cloneInto` returned/jumped via `musttail` to Node `1`'s `cloneInto(&out0->next)`!
   - Nobody on the call stack holds the root pointer `out0` unless the caller of `head.clone()` allocated a root slot and holds a cleanup guard for the **entire half-constructed tree**!
3. And if the caller of `head.clone()` runs a cleanup guard to drop the root `out0` when node `500,000` panics:
   - Node `500,000`'s `Box<Node>` was **already allocated and written into `node_499999.next = #Some(box_500000)`** before tail-calling `Node.cloneInto(node_500000, box_500000.ptr)`!
   - Inside `box_500000`, `b: Bomb` panicked mid-clone, so `box_500000.b` and `box_500000.next` are **uninitialized garbage bytes**!
   - When the root cleanup drops `out0`, it walks down `0 -> 1 -> ... -> 499,999 -> 500,000` and calls `Bomb.drop` and `Option<Box<Node>>.drop` on **uninitialized memory in `box_500000`** — **Undefined Behavior / segfault**!
4. And even if you pre-initialized `box_500000.next = #None` before cloning `b`, what if `Node` has **two** fields with destructors (`b1: Bomb; b2: Bomb; next: Option<Box<Node>>`) and `b2.clone()` panics after `b1.clone()` succeeded?
   - Every node's heap allocation is no longer a valid `Node` during `cloneInto` — it is a partially initialized `Node`!
   - Worse: what if the type is a binary tree (`enum Tree { #Leaf, #Branch(Box<Tree>, Box<Tree>) }`)?
     `cloneInto` can only `musttail` the **second** `Box<Tree>`; the **first** `Box<Tree>` is a normal recursive call, which **still overflows the stack** if the tree is left-heavy!

So Proposal 2(a) requires:
- an extra `cloneInto` method on every `Clone` impl (or a shadow vtable/derivation),
- `unsafe` uninitialized destination pointers through every derived type,
- a special root cleanup walker that knows where the cursor stopped in the heap chain and which fields of the cursor node were initialized when a panic unwound from 500,000 `musttail` frames deep,
- and **still** overflows the stack on left-heavy trees, `Show`, `ToJson`, and `FromJson`!

#### 4. What Should You Do Instead? (Simpler, Sound, Zero New Concepts)

Compare your two actual problems:

##### Problem A: Why are sanitized builds / Wasm failing on `Eq` / `Ord` / `Hash` of a 1M-node list?
Wait: why are you testing `Eq` / `Ord` / `Hash` on a 1,000,000-node linked list in ASan/Wasm in the first place?
1. If it is only because `Box<T>.eq`, `Box<T>.cmp`, `Box<T>.hash` (and `Arc<T>`, `Ref<R, T>`) are in the cycle, look at why `Drop` succeeded in `0.129` (`§4.4`):
   - In `0.129`, you didn't rely on `musttail` for `Drop` (because `Drop` cannot be a tail call: the outer `Box` has to `free` its pointer *after* dropping its payload!).
   - Instead, `0.129` added a tiny runtime mechanism at `Box` / `Vec` / `Arc` boundaries when stack space is low!
2. Even simpler for `Eq`, `Ord`, `Hash` in Proposal 1:
   - Why did `Node.eq -> Option<Box<Node>>.eq -> Box<Node>.eq -> Node.eq` have **three** functions in the loop instead of **one**?
   - Because `Option<Box<Node>>.eq` and `Box<Node>.eq` were not **inlined** into `Node.eq`!
   - Wait: if LLVM inlines `Option<Box<Node>>.eq` and `Box<Node>.eq` into `Node.eq` (or if `Box.eq` and `Option.eq` are marked `alwaysinline` / inlined by the self-hosted compiler), then `Node.eq` directly calls **`Node.eq(a_ptr, b_ptr)`** as a **self-tail-call**!
   - Look at what happens when `Node.eq` self-tail-calls `Node.eq(a_ptr, b_ptr)`:
     1. **Same function:** The caller and callee are the **exact same function `Node.eq`** — identical prototype in C, LLVM, Wasm, and JS! No function-pointer casts in C!
     2. **No stack locals passed:** `a_ptr` and `b_ptr` are heap pointers loaded from `Box<Node>` (`self->next.u.Some.ptr`, `other->next.u.Some.ptr`), **not** addresses in `Node.eq`'s stack frame!
     3. **Even better:** Any self-tail-call `return F(args...)` at the end of `F` in your IR can be lowered by a **15-line pass in the self-hosted compiler** to:
        ```c
        self = next_self;
        other = next_other;
        goto entry;
        ```
        **Stop and read that again!**
        If the compiler (or inliner + self-tail-call loop pass) turns direct self-recursion (or inlined `Box`/`Option` recursion) into `goto entry;`:
        - It uses **$O(1)$ stack in C (even under `-O0` and ASan/TSan!)**.
        - It uses **$O(1)$ stack in LLVM (even under `-O0` and ASan/TSan!)**.
        - It uses **$O(1)$ stack in WebAssembly (without needing `-mtail-call`!)**.
        - It uses **$O(1)$ stack in JavaScript!**
        - It uses **zero `musttail` attributes, zero C function-pointer casts, and zero new spec rules!**

Let's verify this! Why wasn't `Node.eq` a self-tail-call already?
Only because:
1. In `Node.eq`, the last field is `self.next.eq(other.next)`, which calls `Option<Box<Node>>.eq`.
2. `Option<Box<Node>>.eq` matches `#Some(a)` / `#Some(b)` and calls `Box<Node>.eq(a, b)`.
3. `Box<Node>.eq` dereferences the box and calls `Node.eq(a.get(), b.get())`.
Neither `Option.eq` nor `Box.eq` is recursive by itself! Only `struct` and `enum` can be recursive (`§3.3`: *"a recursive type must pass through a nominal declaration"*).
If you inline non-recursive wrappers (`Box.eq`, `Option.eq`, or small derived `eq`/`cmp`/`hash` functions that don't call themselves) — or in the `comptime` derivation of `Eq`/`Ord`/`Hash`, when a field's type is `Box<U>` or `Option<Box<U>>`, or via a trivial tiny-function inliner in your IR — then `Node.eq` contains a **direct tail call to `Node.eq`**!
And a direct tail call from `F` to `F` is trivially lowered to `{ param0 = arg0; param1 = arg1; goto entry; }` on **every single backend (C, LLVM, Wasm, JS)**!

##### Problem B: What about `Clone`?
Choose **Option (d)** (document that `Clone`, like `Show`, `ToJson`, and `FromJson`, recurses to the depth of the value and panics with `stack overflow` if the stack runs out, just as `§5.7` already specifies!).
Why Option (d) is the right choice:
1. **Law 3 / Principle 3 ("Prefer fewer concepts"):** `Drop` had to be bounded-stack (`0.129`, `§4.4`) because **every owned value is dropped implicitly on scope exit and during panic unwinding**, and `§5.7` says *"a panic that escapes a destructor, whenever it runs ... ends the program at once"*. If `Drop` overflowed the stack on a deep list, simply *dropping* a list (or unwinding a task that built a deep list iteratively!) would **abort the entire server process**!
2. By contrast, `Clone.clone()`, `Show.show()`, `ToJson.toJson()`, and `FromJson.fromJson()` are **normal functions, not destructors**:
   - If a task calls `.clone()` or `stringify()` on a million-deep list, `§5.7` already says: *"so does overflowing the stack, which a recursion with no end — on hostile input, say — does: its panic says `stack overflow`, and a margin of the stack is kept for the cleanup it runs."*
   - And because `Drop` *is* bounded-stack (`0.129`), when `.clone()` panics with `stack overflow` at depth 50,000, the task unwinds cleanly, `Drop` frees the 50,000 cloned nodes in bounded stack without overflowing, and the server survives!
3. Neither (a) nor (b) solves `Clone` for binary trees (`#Add(Box<Expr>, Box<Expr>)`), `Vec<Expr>`, `Show`, `ToJson`, or `FromJson` anyway — so adding `cloneInto` + partial-init drop tracking only hacks around one linear linked-list benchmark while complicating the compiler's ownership/drop invariants.

---

### Summary of Recommendations

1. **Reject Proposal 1's general `musttail` spec rule and C function-pointer casts.**
   - Instead, in the compiler IR, inline non-recursive single-match/wrapper calls (`Box.eq`/`cmp`/`hash`, `Option.eq`/`cmp`/`hash`) or run a small inliner before tail-call loopification, and turn any self-tail-call `return F(args...)` into a loop (`goto entry;`). That gives $O(1)$ stack for `Eq`, `Ord`, and `Hash` on **C (including ASan/TSan), LLVM, Wasm, and JS** with zero ABI hacks.
2. **Choose Option (d) for `Clone`.**
   - `Drop` had to be bounded-stack because a panic in `Drop` aborts the whole program (`§5.7`). `Clone` is an ordinary call: if someone clones a million-node linked list, hitting the existing `stack overflow` task panic (`§5.7`) and unwinding cleanly (using `0.129`'s bounded-stack `Drop`!) is already memory-safe, leak-free, and task-isolated.
