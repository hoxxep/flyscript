## 1. The handle

```ts
interface Scope<X> {
  function spawn(self: mut Self, task: once () => void uses Io): Task uses Io;   // was: void
  function fork<T extends Send>(...): Fiber<T> uses Io;                           // unchanged
}
// Clone + Send: a reference-counted handle to the task's record, as an Erlang pid is copyable.
interface Task {
  function cancel(self: readonly Self): void uses Io;  // that task alone; idempotent; no-op once it has ended
  function wait(self: readonly Self): Exit uses Io;    // until the task has finished, cleanup included
}
type Exit = #Done | #Cancelled | #Panicked(String);
```
- Dropping a `Task` leaves the task running (as with `Fiber`).
- `#Cancelled` only if the task actually unwound because of cancellation; a task cancelled that ends normally anyway is `#Done`.
- A spawned task's panic is still reported to stdout even when someone waits on it (Erlang logs crash reports regardless of monitors).
- `wait` on a task of a scope one is not in: the handle is Send, so a supervisor's watcher task can hold a clone. Since the scope outlives all its tasks and handles can escape the scope (Clone + Send, stored in an Arc'd struct?), the record must outlive the scope: refcounted.
- Supervisor shape: children spawned in the supervisor's scope; for each child a watcher task `s.spawn(() => tx.send([i, h.wait()]))`; the supervisor loop receives exits and restarts per strategy, cancelling siblings for all-for-one / rest-for-one with `h.cancel()` then `h.wait()`.

Questions: is `wait` returning the panic message (a String copied out) right, versus Erlang's richer `{'DOWN', Ref, process, Pid, Reason}`? Should `cancel` take a reason? Is Clone+Send handle a hole in structured concurrency (a handle to a task of a scope that has closed: `wait` returns at once with the recorded exit; `cancel` no-op)?

## 2. Stopping a loop that never waits, and stack overflow: one check

Following Go's stackguard0 trick: each fiber has a word `limit` (stack bottom + headroom). Compiled code checks `sp < fiber->limit` (TLS load of the current fiber's pointer, load of limit, compare, predicted branch) on entry to every function in a call-graph cycle and at the back edge of every loop whose body does not perform Io on every iteration. Cancelling a task stores UINTPTR_MAX into its fiber's limit (atomic relaxed, from any thread); the slow path distinguishes: if the fiber is cancelled, unwind as a cancellation (not reported as a panic); else it is a stack overflow: panic "stack overflow" with the limit lowered to the real guard so cleanup has the headroom. Cleanup that itself overflows the headroom hits the guard page and the program dies (SIGSEGV handler prints "stack overflow while unwinding").

Concerns I already see:
- Single-threaded builds: a pure infinite loop never yields, so no other task runs to cancel it. Pure code must NOT become a scheduling point (a Mutex body is pure; yielding there would hold a lock across a scheduling point, and it would break the deterministic simulator's model where pure code is atomic). So in single-threaded builds the poll only fires for a cancellation set before the loop began (which can't happen: cancellation of a runnable task is noticed at its next Io op...). Conclusion: polling only matters with threads (M:N), plus the simulator cannot test it. Acceptable? Or should there be a watchdog thread in single-threaded builds too?
- Cancellation noticed inside a `Mutex.lock` body unwinds it: poisons the mutex, as a panic would. Right, or should lock bodies be exempt (they're bounded? no—they can loop)?
- `join`/`par` halves running on a thief worker: whose flag? The joining task's: the thief's current fiber pointer must point at the owner's limit word for the poll, but its own stack bounds for overflow. So "limit" can't be one word per fiber if a thief runs halves on its own stack. Option: halves on a thief compare against the thief's own stack limit, and cancellation of the owning task sets a flag that the thief's limit mirrors while it runs that half (set on steal, cleared after). Better ideas?
- Indirect calls (closures, fn pointers) can make cycles invisible to the call graph. Draft: treat every function that makes an indirect call, and every function whose address is taken as a closure body, as in a cycle. Too conservative? Go just checks every function with a nontrivial frame.
- Bounded non-recursive chains: the static max depth of a non-recursive chain could exceed the headroom for deep chains with big frames (rare). Go checks every function; Rust checks nothing (guard page + abort). I want the panic, not an abort, because the goal is a server surviving one bad request (deep recursion on hostile input: a JSON parser).
- Cost: compiler compiling itself is deeply recursive (parser, typechecker). Expect ~2-5%?

### Verdicts

- **Decision 1 (`Task` handle as `Clone + Send`):** **Agree with changes.** A refcounted `Clone + Send` `Task` handle does *not* violate structured concurrency because `Io.scope` still bounds the task's execution lifetime (outside the scope, the task is guaranteed dead and `wait` returns immediately). However, four changes are required: (1) `Task` must be a `struct`, not an `interface`, or it cannot be `Clone + Send` by value without `dyn`/`Arc`; (2) spawning a watcher fiber per child (`s.spawn(() => tx.send([i, h.wait()]))`) leaks dead watcher fibers in `Scope`'s task list on every restart and fails to scale — either add a multi-wait or let `spawn` take an optional exit-channel/callback, or reap finished tasks from the scope list immediately; (3) `wait` returning `#Done | #Cancelled | #Panicked(String)` is the right shape (do not add a cancel reason); (4) **do not** unconditionally print a spawned task's panic to stdout if you want clean supervision tests — report it only if no one calls `wait()` (or let a handler/supervisor suppress it).
- **Decision 2 (Go-style `stackguard0` combining cancellation and stack overflow):** **Disagree with cancelling inside pure code via `stackguard0`; Agree with `stackguard0` on every non-leaf function for stack overflow.** Unwinding a pure loop for *cancellation* (as opposed to a panic) has four fatal flaws: (1) a `defer` (`§5.6`: *"Cleanup runs to its end. A cancellation that reaches a task while it runs a `defer` ... waits"*) that calls a pure helper with a `for` loop will immediately self-abort at the helper's loop back-edge because `fiber->limit == UINTPTR_MAX` during cleanup; (2) it breaks Law 4 / `§6.4` (deterministic simulation and single-threaded builds behave differently from multi-core builds, and you **cannot** test pure-loop cancellation in `flyc` or JS/Wasm!); (3) it allows a cancellation to poison a `Mutex` (`§6.2`), turning an ordinary scope cancellation into a server-wide poison cascade; and (4) `stackguard0` on function entry alone misses frames larger than the guard headroom (`let buf: u8[65536]`).
- **Decision 3 (`std/supervise`):** **Agree with changes.** A `Child`'s `start` closure in `struct Child` cannot capture anything borrowed from outside `supervise` (`§4.3`: a closure stored in a struct/Vec escapes and must own only `Send` values!), so `supervise` must take `readonly C` context or allow non-escaping child tables, and each child needs a `Restart` policy (`#Permanent | #Transient | #Temporary`) plus a shutdown mechanism (Wait/Cancel token or channel) so `#AllForOne` can stop healthy siblings cleanly without relying on pure-loop preemption.
- **Decision 4 (Lean proof):** **Agree with changes.** Adding a non-deterministic panic/cancel transition from any expression in λ-fly breaks the existing `Mutex` handler invariant (`mutexEx_ok`, `§9.5`) unless the `Mutex` handler state machine gains a `#Poisoned` state (since previously the body of `lock` was guaranteed to return the box unless it failed, and `lock` bodies have no `Fail`).

#### 1. [Decision 2] Soundness Bug against `§5.6`: Setting `fiber->limit = UINTPTR_MAX` on cancellation aborts `defer`s and `Drop`s at their first loop or recursive call!

In `§5.6`, the specification guarantees:
> **"Cleanup runs to its end.** A cancellation (§6.1) that reaches a task while it runs a `defer` — whether the block is being left normally or the task is already unwinding — waits: the `defer` runs to its end, performing what it performs, and the cancellation takes effect at the task's first scheduling point after it."

Now trace what happens with your `stackguard0` trick (`fiber->limit = UINTPTR_MAX` on `cancel()`) in this program:

```ts
function checksum(bytes: readonly u8[]): u32 {
  let acc: u32 = 0;
  for (const b of bytes) {   // <-- pure loop back-edge checks `sp < fiber->limit`!
    acc = acc.wrappingAdd(b as u32);
  }
  acc
}

export function worker(conn: mut Socket, pending: readonly u8[]): void uses Io, Fail<IoErr> {
  defer {
    // Cleanup must flush a final frame with its checksum before closing.
    const crc = checksum(pending);
    try { conn.write([crc as u8]); } catch (_) {}
  };
  // Suppose `worker` is cancelled while parked in `Io.sleep`, OR cancelled by another core
  // right as `worker` finishes normally and enters `defer`:
  Io.sleep(Duration.secs(10));
}
```
Look at what happens in two cases:
1. **Case A (Cancelled while parked in `Io.sleep`):** `cancel()` sets `fiber->limit = UINTPTR_MAX`. `Io.sleep` wakes and begins unwinding the task for cancellation. During unwinding, the `defer` runs and calls `checksum(pending)`. At the first back-edge of `for (const b of bytes)`, `sp < fiber->limit` fires! If you didn't reset `fiber->limit` when unwinding started, `checksum` unwinds *inside* the `defer`!
2. **Case B (Cancelled from Core 2 *while* Core 1 is already inside `defer` or `Drop`):** Suppose Core 1 is exiting `worker` normally (or already unwinding) and is currently inside `defer { const crc = checksum(pending); ... }` or inside `Drop.drop` (e.g., `HashMap.drop` looping over buckets to drop keys and values!). At that instant, Core 2 calls `task.cancel()`, which atomically stores `UINTPTR_MAX` into `fiber->limit`!
   - On the very next iteration of `HashMap.drop`'s loop (or `checksum`'s loop), `sp < fiber->limit` triggers inside `Drop.drop` / `defer`!
   - Unwinding from inside `Drop.drop` either aborts the entire program (`§5.7`: panic in cleanup) or skips dropping the remaining elements of the `HashMap` (leaking memory and violating `§5.6` and `§9.4` #5 Deterministic Destruction)!

**Even if you try to suppress cancellation in `fiber->limit` while `in_cleanup > 0`:**
Look at the next problem with cancelling pure code (`Mutex.lock`).

#### 2. [Decision 2] Unwinding a `Mutex.lock` body on *cancellation* turns an ordinary `cancel()` into a server-wide `Mutex` poison cascade, and breaks the simulator (`§6.2`, `§6.4`)

You noticed two halves of this in your prompt:
- *"Cancellation noticed inside a `Mutex.lock` body unwinds it: poisons the mutex, as a panic would. Right, or should lock bodies be exempt?"*
- *"Conclusion: polling only matters with threads (M:N), plus the simulator cannot test it."*

Put those two together in a concrete server program:

```ts
import { Mutex } from "std/sync";
import { HashMap } from "std/collections";

export function runServer(): void uses Io {
  const sessions = Mutex.new(HashMap.new<u64, Vec<u64>>());
  Io.scope((s) => {
    const h1 = s.spawn(() => {
      // Task 1 updates its session list inside `sessions.lock`:
      sessions.lock((map) => {
        let xs: Vec<u64> = Vec.new();
        for (const i of 0..1000) { xs.push(i as u64); } // <-- loop back-edge!
        map.insert(1, xs);
      });
    });

    // Task 2 cancels Task 1 (e.g. client disconnected or request timed out):
    h1.cancel();
  });
}
```
Look at what happens if `h1.cancel()` can unwind `h1` at the loop back-edge inside `sessions.lock`:
1. **Cancellation is normal control flow (timeouts, client disconnects, `#AllForOne` restarts); panics are bugs (`§5.7`).**
   If `h1.cancel()` happens to hit while `h1` is inside `sessions.lock(...)` (which is a completely bug-free `for` loop!), `h1` unwinds out of `sessions.lock` and **poisons `sessions`**, killing every other connection task in the server on their next `sessions.lock(...)`!
2. **Even outside `Mutex.lock`, pure functions mutate `&mut` parameters (`§4.1`):**
   Suppose a task holds a borrowed `mut` reference (or is inside a helper function before an `Io` point) and is cancelled at a pure loop back-edge. In Go, Java, Kotlin, Tokio, and Trio, **cancellation is strictly cooperative at suspension (`Io`) points** — neither Go (`context.Context`), nor Tokio (`JoinHandle::abort`), nor Trio, nor Kotlin (`Job.cancel`) preempts pure CPU loops on `cancel()`! Why? Because preemptive cancellation of pure code makes every loop back-edge an asynchronous exception point, which destroys invariants and cannot be tested deterministically.
3. **And what about Erlang?** In Erlang, processes share **zero** mutable memory (no `mut T`, no `Mutex<T>`) and have **no `defer` or `Drop` destructors** on the stack — killing an Erlang process just frees its private heap. In Flyscript, tasks share `Mutex<T>` and run `Drop`/`defer` on unwind.
4. **And in the deterministic simulator (`§6.4`), JavaScript (`§11.2`), and WebAssembly (`§8.3`):**
   As you noted, a single-threaded cooperative scheduler *never* switches tasks during a pure loop, so `h1.cancel()` can **never** interrupt a pure loop in `flyc`, `--js`, `--wasm`, or `FLY_WORLD` simulation! Having semantics that only occur under multi-core thread races and can never be reproduced in the deterministic simulator violates Goal 4 (`§1`: *"Testability by construction: because I/O is an effect, any program can run under a deterministic simulator"*).

**Fix (Clean, 100% consistent across all backends and the simulator):**
- **Keep `cancel()` strictly at `Io` scheduling points** (just as `§6.1` Rule 3 already states: *"the body and every other task stop at their next `Io` operation and unwind — a task in cleanup finishes it first"*).
  - Then `cancel()` **never** unwinds a `Mutex.lock` body (because `Mutex.lock`'s body is pure!), **never** interrupts `Drop` or `defer` (`§5.6`), and behaves **identically** in native multi-core, single-core, Wasm, JS, and the deterministic simulator!
- **Use the `sp < fiber->limit` check ONLY for stack overflow (which IS a deterministic bug/panic, `§5.7`)!**
  See Problem 3 for the exact details of stack-overflow checking.

#### 3. [Decision 2] Stack-overflow check via `sp < fiber->limit`: three concrete holes (large frames, `join`/`par` thieves, and C/Wasm backends)

Even when `sp < fiber->limit` is used purely for stack overflow, there are three subtle bugs in the draft mechanism you must avoid:

**Hole 3A: A function with a frame larger than `headroom` skips past `fiber->limit` into unmapped memory.**
```ts
function bigFrame(n: usize): u8 {
  let buf: u8[131072] = repeat(0); // 128 KB frame on the stack!
  if (n > 0) { bigFrame(n - 1) } else { buf[0] }
}
```
If `fiber->limit = stack_bottom + 16384` (16 KB headroom), and you check `sp < fiber->limit` *after* the function prologue has subtracted `131072` from `RSP` (or if `RSP` wraps / jumps completely below `stack_bottom` into the OS guard page or adjacent heap allocation before `sp < fiber->limit` is even reached!), then touching `buf` or running the prologue itself segfaults instead of panicking!
- **Fix for LLVM / C:**
  1. In the compiler pass that inserts stack checks, you already know the local stack frame size `F` of each function (sum of `let` allocas in `ir.fly`).
  2. Check `(uintptr_t)__builtin_frame_address(0) - F < fiber->limit` (or in LLVM IR, check `sp - F < limit` in the entry block *before* touching any large stack array, and reject or heap-box frames where `F` alone exceeds the fiber stack size!).
  3. Which functions need the check? If you want any deep non-recursive chain or hostile JSON input (`A.1`) to panic cleanly rather than hitting a guard page, check in **every non-leaf function** (any function that makes at least one call).
     - Why every non-leaf function instead of call-graph SCCs? Because (a) leaf functions cannot grow the stack further and have no calls, so skipping leaf functions already eliminates the check from `isSpace`, `eat`, `Vec.len`, `Option.isSome`, getters, and math helpers; (b) for non-leaf functions, `sp < worker_or_fiber_limit` is 2 instructions (a load from a pinned register/TLS and a predicted-not-taken branch), which costs **< 1%** on `selfhost` (Go measures ~1.2% across all functions); and (c) you don't have to worry about indirect closure calls hiding a cycle or a 50-deep non-recursive chain overflowing!

**Hole 3B: `join` / `par` (`§6.5`) running on a thief worker thread's native OS stack.**
In your prompt you asked:
> *"`join`/`par` halves running on a thief worker: whose flag? The joining task's: the thief's current fiber pointer must point at the owner's limit word for the poll, but its own stack bounds for overflow."*

Once you drop pure-loop cancellation (Problem 2), this complication **completely disappears**!
- Every execution context (each fiber, and each worker thread's native stack) simply has **its own** `stack_limit: uintptr_t` stored in a single TLS variable `__thread uintptr_t fly_stack_limit;`!
- When a worker switches to Fiber F, it sets `fly_stack_limit = F->stack_limit;`.
- When a thief worker runs a `join`/`par` half on its own stack (or on a fiber), `fly_stack_limit` is already that stack's limit!
- Every non-leaf function just checks `(uintptr_t)__builtin_frame_address(0) - F < fly_stack_limit` — **one TLS load** (no double pointer indirection `tls_fiber->limit`!), works identically on the main stack, on a fiber stack, and on a `join`/`par` thief worker!
- And when `fly_stack_overflow()` triggers: it lowers `fly_stack_limit` by ` UNWIND_HEADROOM` (e.g. 16 KB) so `Drop` and `defer` can run, sets `fly_in_stack_overflow = 1`, and raises `panic("stack overflow")` (`§5.7`). When unwinding finishes at the task root, if the task ends or resets, the limit is restored.

#### 4. [Decision 1 & 3] Watcher-Task-Per-Child Pattern in `Io.scope` Leaks Dead Tasks Across Long-Lived Supervisor Restarts (`§6.1`)

Look closely at how you proposed implementing `supervise` using `Scope.spawn` and `Task.wait`:
> *"Supervisor shape: children spawned in the supervisor's scope; for each child a watcher task `s.spawn(() => tx.send([i, h.wait()]))`; the supervisor loop receives exits and restarts per strategy"*

Trace what happens when a supervised child crashes and is restarted 100,000 times over the life of a server inside `Io.scope((s) => ...)`:
```ts
// Inside `supervise`:
Io.scope((s) => {
  // Every time child `i` is started or restarted:
  const h: Task = s.spawn(() => child.start());
  s.spawn(() => { tx.send([i, h.wait()]); }); // <-- A SECOND task spawned per restart!
  ...
});
```
1. Look at `Io.scope`'s task list in the runtime (`rt`): if `Io.scope` links every spawned task into `scope->tasks` so it can wait for all of them when the scope exits (or cancel all of them if the scope is cancelled), what happens to a `spawn`ed task that **finishes early** while `Io.scope` runs forever (as a server or supervisor scope does)?
   - Unless a finished `spawn` task **immediately unlinks itself from `scope->tasks` and frees its fiber/stack** (leaving only the tiny refcounted `Task` exit record if a `Task` handle is still alive), restarting a child 10,000 times will accumulate **20,000 dead fibers and stacks** in `scope->tasks` — an unbounded memory leak!
2. Even if finished tasks unlink and free their fiber stacks immediately upon completion, spawning **two** full stackful fibers for every supervised child (one to run the child, and a second stackful fiber whose entire job is to block in `h.wait()` and push `[i, exit]` to a channel!) wastes an extra fiber stack per child!

**Fix (Two small adjustments, zero extra concepts):**
1. **In the runtime (`rt`):** When any `spawn`ed task finishes (after its unwinding/cleanup completes), it **must** immediately free its fiber stack and unlink itself from `scope->tasks` (decrementing `scope->active_count`), keeping only the tiny refcounted `TaskState` (`{ refcount: Atomic<usize>, status: u8, panic_msg: String, wait_key: WaitKey }`, ~48 bytes) if `refcount > 0` (i.e. if the caller kept the returned `Task` handle instead of dropping it).
   - Bonus: if the caller writes `s.spawn(() => serveOne(conn, db));` and discards the returned `Task` handle (`§5.6` temporary dropped at the `;`), `Task.drop` runs immediately, so when `serveOne` finishes, `refcount` hits 0 and the 48-byte `TaskState` is freed too! Zero leaks in `serve` (`§A.7`)!
2. **To avoid a watcher fiber per child in `supervise`:**
   Either:
   - Add `Task.waitAny(tasks: readonly Task[]): [usize, Exit] uses Io` (or `Scope.spawnOn(task, exitTx: readonly Sender<[usize, Exit]>, id: usize)` / an optional callback), **OR**
   - Give `Task` a method `function notify(self: readonly Self, tx: readonly Sender<[usize, Exit]>, tag: usize): void uses Io` that registers the channel on the `TaskState` so when the task exits, its exit handler pushes `[tag, exit]` directly into `tx` (or wakes `tx`'s receiver) with **zero watcher fibers**!
   Wait — look how clean that is: if a child itself just runs a small wrapper inside its *own* spawned task:
   Wait: why did you need a separate watcher task in the first place?!
   Because if the child panics, the panic unwinds the child task to its root! A `defer` inside the child task runs *during* unwinding, before the final `Exit` (`#Done | #Cancelled | #Panicked(msg)`) is determined!
   So the child task *cannot* send its own `Exit` from inside Flyscript code unless `spawn` (or `Task`) does it at the task root after unwinding finishes.
   Let's compare:
   - If you don't want any extra method on `Task`, can `supervise` in `std/supervise` be a runtime-backed std function, or use `Task.waitAny(tasks: readonly Task[]): [usize, Exit] uses Io`?
   - `waitAny(tasks: readonly Task[]): [usize, Exit] uses Io` is **15 lines in the runtime** (parks the caller on the tasks' wait list until any `tasks[i]` is terminal, then returns `[i, tasks[i].exit]`) — and it eliminates both the channel AND all N watcher fibers!

```ts
// With `waitAny(tasks: readonly Task[]): [usize, Exit] uses Io`:
const [idx, exit] = waitAny(handles);
```
Look at that: no channel needed, no watcher fibers needed, works with any `Vec<Task>`, and is trivial in both the native runtime and the deterministic simulator!

#### 5. [Decision 1] `Task` must be a `struct`, not an `interface`, and Panic Reporting Must Not Pollute Handled Supervision (`§3.4`, `§5.7`)

Look at your draft signature in Decision 1:
```ts
interface Task {
  function cancel(self: readonly Self): void uses Io;
  function wait(self: readonly Self): Exit uses Io;
}
```
In Flyscript (`§3.4`):
- An `interface` is a trait bound (`<T extends Task>`) or a fat pointer (`dyn Task`), **not** a concrete value type that `Scope.spawn` can return by value (`): Task`) or that can implement `Clone` and `Send`!
- Just look at `std.md` / `§10.1`: concrete opaque runtime handles (`Socket`, `Mutex<T>`, `Sender<T>`, `Receiver<T>`, `Atomic<T>`) are declared as `export struct Task { ... }` (or `export struct Task;` in `.d.fly`) with `impl Task { ... }`, `impl Clone for Task`, and `impl Send for Task` (by having no raw pointer visible outside `std` or via runtime `Send`).
- Note that `Scope<X>` and `Fiber<T>` in `§6.1` are currently written as `interface` in the spec text, which is actually a slight spec inconsistency with `§3.4` (`Scope` and `Fiber` are used as concrete types `mut Scope<X>` and `Fiber<T>`, not `dyn Scope<X>`!). Making `Task` (and ideally `Scope<X>` and `Fiber<T>`) `export struct` in `.d.fly` with `impl` methods is much cleaner and obeys `§3.4`.

**Second, on panic reporting for `spawn`ed tasks:**
You wrote:
> *"A spawned task's panic is still reported to stdout even when someone waits on it (Erlang logs crash reports regardless of monitors)."*

Wait: think about how your own test suite (`tests/`) and simulator (`§6.4`) work!
1. In your test suite, every test compares **exact `stdout` output** across all 4 backends (`flyc`, JS, C, LLVM)!
2. If you write a test for `Task.wait()` returning `#Panicked("boom")` or a test for `std/supervise` restarting a panicking worker 3 times, and every panic unconditionally prints `panic: boom` to `stdout`, What happens when **two** spawned tasks panic concurrently on a multi-core machine?

3. If `spawn` only prints the unhandled panic message when the `Task` handle was **dropped without calling `wait()`** (or when the task finishes and its `Task` handle has already been dropped without a waiter), then:
   - Fire-and-forget `s.spawn(() => serveOne(conn, db));` (where the `Task` handle is immediately dropped at `;`) **still reports the panic immediately** when the task crashes!
   - Supervised or monitored tasks (`const t = s.spawn(...); ... t.wait()`) return `#Panicked(msg)` cleanly to the waiter without polluting `stdout` (and `supervise` itself can log if desired)!

```ts
  const children: Vec<Child> = [
    Child { name: "a".toString(), start: () => workerA(totals) }, // ERROR!
    Child { name: "b".toString(), start: () => workerB(totals) }, // ERROR!
  ];
  supervise(#OneForOne, children, { restarts: 5, within: Duration.secs(10) });
}
```
**Why is this rejected by the type checker?**
Look at `§4.3` (*Closures*) and `§4.2` (*Second-class values*):
1. In `() => workerA(totals)`, if the closure borrows `totals` (`readonly Mutex<...>`), the closure is **class 2** (`§4.3`: *"A closure that holds a borrow is class 2: it can be passed down but not returned or stored."*).
2. `Vec<Child>` requires `Child` to be **class 1** (`§4.2`: *"Containers hold first-class values. A nominal type's type parameters range over class-1 types unless the type is a `view`"*).
3. Even if `start: () => void uses Io` is treated as an *escaping* closure because it is stored in the struct `Child` (`§4.3`: *"A closure that escapes — returned, or stored in a record, tag or list by the function that creates it — instead takes ownership of what it captures, by move where it is made"*), then the **first** `Child` moves `totals` by value, and the **second** `Child` fails with **use-after-move of `totals`**! You would be forced to wrap everything in `Arc<Mutex<...>>` and `.clone()` it for every child, contradicting `§6.2`!

**Fix for `std/supervise`:**
Pass a slice of `view struct Child` (or pass a shared `ctx: readonly C` parameter!), because a slice `readonly Child[]` lent directly to `supervise(...)` is **class 2** (`view`) and never escapes!
Let's check `view struct Child`:
```ts
export type Strategy = #OneForOne | #AllForOne | #RestForOne;
export type Restart  = #Permanent | #Transient | #Temporary;

export view struct Child {
  name: str;
  restart: Restart;
  start: () => void uses Io;   // May borrow `readonly` outer bindings!
}

export function supervise(
  strategy: Strategy,
  children: readonly Child[],
  limit: { restarts: u32; within: Duration },
): void uses Io;
```
Look at what changing `struct Child` to `view struct Child` and `Vec<Child>` to `readonly Child[]` (with `start` capturing only `Send` borrows, or passing `ctx: readonly C` where `C extends Send`) does:
-Wait: inside `supervise`, `supervise` calls `s.spawn(() => children[i].start())`.
For `s.spawn` inside `supervise` to call `children[i].start()`, what does `§6.1` Rule 6 say?
> *"Only inside the body of its `Io.scope` is it known what outlives the scope: a task started elsewhere — by a helper function given `mut Scope<X>` — moves in everything it captures and cannot capture anything that borrows"*

Look at `supervise`: `supervise` **opens its own `Io.scope((s) => ...)` inside `supervise`!**
Any parameter of `supervise` (such as `children` or `ctx: readonly C`) is declared **outside** `supervise`'s `Io.scope((s) => ...)`!
So inside `supervise`, `children` (or `ctx: readonly C`) **outlives `supervise`'s `Io.scope`**!
However, `§6.1` Rule 6 requires that anything a spawned task captures `readonly` from outside `Io.scope` must be **`Send`**!
- Is a class-2 closure `start: () => void uses Io` considered `Send` by `§4.4`?
  Look at `§4.4`:
  > *"`T` is `Send` when it is class 1 and owns no raw pointer or runtime handle... Every function value is `Send`, since an escaping closure owns only `Send` values (§4.3); a closure that holds a borrow carries it as a loan, which a task cannot take (§6.1)."*
  **BINGO!** Read that sentence in `§4.4` again:
  A closure that holds a borrow is **not `Send`**, so a task inside `supervise` **cannot capture a borrowed closure**, whereas a first-class escaping closure `start: () => void uses Io` **is `Send`** (`§4.4`: *"Every function value is `Send`, since an escaping closure owns only `Send` values"*), **or** if `supervise` is parameterized by `<C extends Send>(ctx: readonly C, ...)`:
  ```ts
  export struct Child<C = void> {
    name: String;
    restart: Restart;
    start: (ctx: readonly C) => void uses Io;
  }
  export function supervise<C extends Send>(
    ctx: readonly C,
    strategy: Strategy,
    children: readonly Child<C>[],
    limit: { restarts: u32; within: Duration },
  ): void uses Io;
  ```
  Trace how `supervise( { db, totals }, #OneForOne, [ ... ], ... )` works with `Child<C>`:
  1. The caller passes `{ db, totals }` (or any `readonly C` where `C extends Send`, or `()` if none) as `ctx`!
  2. Each `Child<C>`'s `start: (ctx: readonly C) => void uses Io` is a pure function pointer / `Send` closure that takes `ctx: readonly C` as its parameter instead of capturing borrows!
  3. Inside `supervise`, `ctx: readonly C` is a `Send` binding declared outside `supervise`'s `Io.scope((s) => ...)`, so `s.spawn(() => child.start(ctx))` captures `readonly ctx` and `readonly child` — both of which are `Send` (`C extends Send`, `Child<C>` is class 1 and `Send`)!
  4. **Zero `Arc`s needed, zero borrow-capture violations, 100% legal under `§4.3`, `§4.4`, and `§6.1` Rule 6!**

- **Also add `Restart` policy (`#Permanent | #Transient | #Temporary`) to `Child<C>`:**
  - `#Permanent`: always restarted (whether `#Done`, `#Cancelled`, or `#Panicked`).
  - `#Transient`: restarted only on `#Panicked(_)` (if it exits `#Done` or `#Cancelled`, it stays down).
  - `#Temporary`: never restarted (nor does its exit trigger `#AllForOne` / `#RestForOne`).
  In OTP, without `#Transient`, you cannot supervise one-off workers that should restart on crash (`#Panicked`) but stay finished when they succeed (`#Done`). It is 6 lines of `match` in `supervise`.

#### 7. [Decision 4] The Lean Proof (`§9.5`): Adding a Panic Step Requires Updating the `Mutex` Handler Invariant (`mutexEx_ok`)

In Question 4, you ask:
> *"Panic becomes a step from any expression (the calculus is A-normal form), dropping the task's continuation as a dropped continuation already does (§9.5). Cancellation polled in pure code is the same step. Any obstacle you see?"*

Yes — check `mutexEx_ok` (`§9.5`) in `proof/`:
1. In the current Lean proof (`§9.5`):
   > *"a `Mutex` of a box, whose lock moves the box out to the task that locks it, which may give way while it holds it, the other tasks finding it busy, and whose unlock moves it back"*
2. Why did `mutexEx_ok` go through previously?
   Because previously, the task holding the box between `lock` and `unlock` could not fail (or if it failed before `unlock`, wait — in `§6.2` `Mutex.lock`'s body has no `Fail` effect!). And panics previously terminated the entire program at once (`§9.5`: *"Unless it panics, which ends it at once"*), so the proof never had to step *past* a panic inside a task!
3. Now, if a task can **panic and unwind** from any expression while holding the `Mutex`'s box (between `lock` and `unlock`), and the other tasks in the scope continue running (because the panicking task was `spawn`ed):
   - When the panicking task unwinds its continuation, its scope drops the box it took from `lock` (or returns a poison token to the `Mutex` handler).
   - What happens when a **second** task in the same scope then performs `lock` on the `Mutex` handler?
   - Previously, the `Mutex` handler's state was `Option<Box>` (`#Some(b)` when unlocked, `#None` when locked). If the first task panics and drops `b` without calling `unlock`, the `Mutex` handler's state is stuck at `#None` forever — and if another task calls `unlock` or `lock`, or when the `Mutex` handler scope ends, its invariant must know that `#None` (or `#Poisoned`) is a valid terminal state where the box was already freed (or held as poisoned)!
- **Fix in `proof/`:**
  - Either model `Mutex.lock(body)` in the proof as keeping the box in the `Mutex` handler under a `#Poisoned(box)` tag if the task panics before `unlock` (matching `§6.2`: *"it keeps the state where it is, and every `lock` from then on panics. The state is not dropped by the panicking task ... it is dropped with the mutex, or by `reset(v)`"*), **or**
  - Have the unwinding of `lock`'s frame perform the handler's `poison` operation so the `Mutex` handler transitions to `#Poisoned` and any subsequent `lock` by another task takes the panic step!
  - Either way, `program_ok_sched` (that at the end of the program every allocated cell not in the result was freed exactly once) still holds!

### Smaller Points

- **`cancel()` taking a reason (Decision 1):** Do **not** add a reason argument to `cancel()`. In Go (`context.WithCancelCause`) and Erlang (`exit(Pid, Reason)`), custom cancel reasons exist only because they conflate cancellation with error propagation. In Flyscript, `spawn` tasks return `void` and `Fail<E>` is separate (`fork`). Keeping `cancel()` zero-argument and `Exit = #Done | #Cancelled | #Panicked(String)` avoids allocating a `String` on every cancellation.
- **`#Cancelled` vs `#Done` race (Decision 1):** Your rule (*"`#Cancelled` only if the task actually unwound because of cancellation; a task cancelled that ends normally anyway is `#Done`"*) is the exact right rule (it matches Tokio's `JoinError::is_cancelled` and Kotlin's `Job`). It means `Exit` is a factual record of how the task terminated, not whether `cancel()` was ever called on its handle.
- **`wait` called by multiple clones of `Task` (Decision 1):** Since `Task` is `Clone + Send` and `wait(self: readonly Self): Exit uses Io` takes `readonly Self`, two tasks can call `h.wait()` concurrently on clones of the same `Task`. Make sure `TaskState`'s wait list wakes **all** parked waiters when the task transitions to terminal (like a broadcast / latch, not a single-waiter `Fiber.join`), and that calling `h.wait()` *after* the task is already terminal returns a `.clone()` of `#Panicked(msg)` immediately without parking.
